# LEOGO-SEC-001 — untrusted runtime reporting

Original severity: Medium. Current baseline: `acde466b4e03bed61a00dda8ca4afd4efd853e31`. The existing production recorder body matches the repository's runtime-connectivity migration; this patch targets only that known definition.

Local PostgreSQL reproduction confirmed that an anonymous report with `p_severity='critical'` becomes Critical. The candidate ignores caller severity; browser observations are labelled `client_unverified` and capped at Warning. Only a gateway-verified `service_role` backend can derive Critical from JavaScript exceptions or HTTP 5xx. Existing Critical incidents, fingerprints, counters, statuses, historical rows, Diagnosis checks and recovery logic are not rewritten.

`p_client_id` no longer determines the rate bucket. Signed-in reports use verified `auth.uid()` plus portal; guests share a portal bucket, bounded at 60 stored events per 10 minutes. An advisory transaction lock prevents concurrent checks in a bucket from racing. This avoids trusting spoofable forwarding headers and needs no IP retention. It deliberately trades guest capacity for abuse resistance: one attacker or a busy shared guest portal can exhaust the quota. Distributed abuse and gateway throttling remain a staging/design review item. Five valid portals bound guest capacity to 300 events per 10 minutes. This is not a claim of complete anti-abuse protection.

The private sanitizer fixes SQL regex escaping and scrubs emails, phone/ID-like numbers, token/key-like values, labelled private credentials/accounts and URLs. Metadata is allowlisted, malformed/oversized objects are rejected, operation/source paths are constrained, and private tables remain inaccessible. New helper EXECUTE is revoked from public/anon/authenticated; it runs through the existing SECURITY DEFINER recorder. No RLS is weakened. The recorder's signature and existing permissions stay unchanged.

15 isolated PostgreSQL assertions passed: baseline forged Critical, anonymous report, authenticated report, rotated IDs, duplicate deduplication, guest quotas, malformed metadata, PII scrubbing, JS exception, HTTP 500, HTTP 401, table access denial and trusted-backend classification. PGlite uses synthetic role/session context and actual recorder SQL; it is not a Supabase JWT/API staging test. Multi-connection contention, genuine gateway identity, alert severity policy and signed-in browser reporting remain pending. The rollback SQL covers the guest subset in a fresh staging database.

Forward-only migration: `20261004113510_harden_guest_runtime_telemetry_phase1.sql`, generated by Supabase CLI. NOT APPLIED to production. Approval and isolated Supabase staging validation are required before any release. No guest/forged/flood test reports were inserted in production.

## Revised staging candidate

The candidate now rejects messages larger than 8192 bytes before regular-expression scrubbing and sanitizes source values before route classification. Source/code/operation key-like values cannot leak through their structured allowlists. Applied only to isolated staging uxikemfrzqatsbqutida, not production.

Nine real Supabase API checks passed: anonymous fake Critical, rotated-ID duplicate, authenticated JavaScript exception, HTTP 500, expected HTTP 401, malformed metadata, oversized message, sensitive test values and 75 concurrent requests with rotating IDs. The guest pickup portal bucket retained exactly 60 events; 19 of the concurrent calls were rate limited. Database inspection retained 60 guest Warning events and one authenticated Warning; no tested sensitive values survived.

Severity deliberately treats every browser report as unverified Warning, regardless of claimed Critical/HTTP500. Trusted backend classification is unchanged. Existing production Critical incidents/history are not rewritten. A global per-portal guest quota can still be exhausted by an attacker; a trusted gateway is a separate design decision. Staging API checks do not establish visual/mobile UI behavior. Production release remains blocked on browser verification, migration-baseline review and approval.
